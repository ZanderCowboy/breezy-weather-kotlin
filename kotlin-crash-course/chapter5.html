What are Interfaces?

Interfaces are like contracts or blueprints in Kotlin. They define what a class should do without specifying how it should do it. Think of them as a promise: "If you implement me, you must provide these functions!" Perfect for creating flexible, testable, and maintainable code. 🤝

Contract definition - what must be implemented

No concrete implementation - just signatures

Abstraction layer - hide implementation details

Type safety - compiler enforced contracts

🤔 Why Use Interfaces?

🎯 Real-World Analogy:

Think of a USB port on your computer. It's an interface that says: "Any device that implements USB can plug into me." Your mouse, keyboard, phone charger - they all implement the USB "interface" differently, but they all work with the same port!

✅ With Interfaces

  • Flexible implementations
  • Easy to test with mocks
  • Loose coupling
  • Multiple inheritance possible
  • Clear contracts

❌ Without Interfaces

  • Tight coupling to concrete classes
  • Hard to test
  • Difficult to change implementations
  • Less flexible architecture
  • Harder to maintain

⚖️ Interface vs Abstract Class

🔗 Interface

interface Drawable {
    fun draw()
    fun getArea(): Double
    
    // Can have default implementation
    fun describe() = "Shape"
}
  • Only abstract by default
  • Multiple inheritance
  • No constructor
  • Can have default methods

🏗️ Abstract Class

abstract class Shape {
    abstract fun draw()
    var color: String = "blue"
    
    // Concrete implementation
    fun move() { /*...*/ }
}
  • Can mix abstract/concrete
  • Single inheritance only
  • Can have constructor
  • Can store state

💡 Rule of Thumb: Use interfaces for "can do" relationships (Flyable, Drawable) and abstract classes for "is a" relationships (Animal, Vehicle).

✨ Benefits of Interfaces

🚀 Architecture Benefits:

  • Dependency Inversion: Depend on abstractions, not concretions
  • Open/Closed Principle: Open for extension, closed for modification
  • Single Responsibility: Each interface has one clear purpose
  • Interface Segregation: Many specific interfaces > one general

🧪 Testing Benefits:

  • Mockability: Easy to create test doubles
  • Isolation: Test classes in isolation
  • Fast Tests: No need for real implementations
  • Reliability: Consistent test behavior

// From DatabaseHandler.kt - Clean database abstraction
interface DatabaseHandler {

    // 🚀 Suspend function for coroutines - async database operations
    suspend fun <T> await(
        inTransaction: Boolean = false, 
        block: suspend Database.() -> T
    ): T

    // 📋 Suspending list operations with generics
    suspend fun <T : Any> awaitList(
        inTransaction: Boolean = false,
        block: suspend Database.() -> Query<T>,
    ): List<T>

    // 🌊 Reactive streams with Flow - real-time data updates
    fun <T : Any> subscribeToList(
        block: Database.() -> Query<T>
    ): Flow<List<T>>

    // 💾 Single item operations
    suspend fun <T : Any> awaitOne(
        block: suspend Database.() -> Query<T>,
    ): T?

    // 🌊 Reactive single item subscription
    fun <T : Any> subscribeToOne(
        block: Database.() -> Query<T>
    ): Flow<T?>
}

🚀 Advanced Kotlin Features

  • suspend fun - ⚡ Coroutine functions for async operations
  • <T> - 🧬 Generic type parameters (works with any type)
  • T : Any - 🛡️ Type constraints (T must be non-null)
  • Flow<List<T>> - 🌊 Reactive streams for real-time data
  • Database.() -> T - 🎯 Extension function types
  • inTransaction: Boolean = false - 🔧 Default parameters

🎯 Pro Tip: This interface combines multiple advanced Kotlin features to create a powerful, type-safe, and async database API!

🧬 Generics Explained

Generics allow you to write code that works with any type while maintaining type safety:

// Generic function breakdown
suspend fun <T : Any> awaitList(
    inTransaction: Boolean = false,
    block: suspend Database.() -> Query<T>,
): List<T>

// Usage examples - same function, different types!
val locations: List<Location> = db.awaitList { 
    locationQueries.selectAll() 
}

val weatherData: List<WeatherEntity> = db.awaitList { 
    weatherQueries.selectAll() 
}

🔍 Generic Constraints:

  • T : Any - T must be non-null
  • T : Comparable<T> - T must be comparable
  • T : Serializable - T must be serializable
  • T : WeatherData - T must extend WeatherData

🌊 Coroutines & Flow

Modern asynchronous programming in Kotlin:

// Suspend functions for async operations
suspend fun loadWeatherData(): WeatherData {
    return databaseHandler.awaitOne {
        weatherQueries.getLatest()
    } ?: WeatherData.empty()
}

// Flow for reactive data streams
fun observeWeatherData(): Flow<WeatherData?> {
    return databaseHandler.subscribeToOne {
        weatherQueries.getLatest()
    }
}

// Usage in UI
class WeatherViewModel {
    val weatherData = observeWeatherData()
        .stateIn(viewModelScope, SharingStarted.Lazily, null)
}

🎯 Benefits:

  • Non-blocking: UI stays responsive
  • Reactive: UI updates automatically when data changes
  • Efficient: Only updates when necessary
  • Lifecycle-aware: Handles Android lifecycle automatically

Implementing Interfaces

Create Interface Implementations

Learn how to implement and use interfaces effectively

// Weather data source interface
interface WeatherDataSource {
    suspend fun getCurrentWeather(location: Location): WeatherData?
    suspend fun getForecast(location: Location): List<ForecastData>
    
    // Default implementation - can be overridden
    fun getSourceName(): String = "Unknown Source"
}

// OpenWeatherMap implementation
class OpenWeatherMapSource : WeatherDataSource {
    override suspend fun getCurrentWeather(location: Location): WeatherData? {
        // API call implementation
        return api.getCurrentWeather(location.latitude, location.longitude)
            .toWeatherData()
    }
    
    override suspend fun getForecast(location: Location): List<ForecastData> {
        // Forecast API implementation
        return api.getForecast(location.latitude, location.longitude)
            .map { it.toForecastData() }
    }
    
    override fun getSourceName() = "OpenWeatherMap"
}

// Alternative implementation for testing
class MockWeatherSource : WeatherDataSource {
    override suspend fun getCurrentWeather(location: Location) = 
        WeatherData(temperature = 25.0, description = "Sunny")
        
    override suspend fun getForecast(location: Location) = 
        emptyList<ForecastData>()
        
    override fun getSourceName() = "Mock Source"
}

Interface Best Practices

  • Single Responsibility: Each interface should have one clear purpose
  • Cohesive Methods: All methods should be related to the interface's purpose
  • Default Implementations: Provide sensible defaults when possible
  • Naming Convention: Use descriptive names ending in -able, -er, or describing capability
  • Dependency Injection: Use interfaces with DI for flexible architecture
